# Задание 1. Стратегия шардирования, репликации и кэширования

## Контекст

Онлайн-магазин «Мобильный мир» упал во время Чёрной пятницы из-за перегрузки MongoDB.
Узкое место — очереди записи заказов и повторяющиеся read-запросы к одним и тем же данным.

Решение: три уровня оптимизации — шардирование (writes), репликация (отказоустойчивость), кэширование (reads).

---

## Коллекции и их стратегии

| Коллекция | Шардирование | Кэширование | Обоснование |
|---|---|---|---|
| `orders` | `{ user_id: "hashed" }` | нет | основной write-путь, нагрузка пропорциональна числу пользователей |
| `users` | `{ _id: "hashed" }` | нет | регистрации и сессии растут линейно с трафиком |
| `products` | не шардируется | Redis, TTL 60s | каталог читают все одновременно — шардирование не помогает, нужен кэш |

---

## Вариант 1 — Шардирование

**Файл схемы:** `task1_v1_sharding.drawio`

### Конфигурация

| Параметр | Значение |
|---|---|
| База данных | `somedb` |
| Количество шардов | 2 |

### Ключи шардирования

| Коллекция | Ключ | Причина |
|---|---|---|
| `orders` | `{ "user_id": "hashed" }` | каждый пользователь пишет в свой шард, нагрузка на write равномерна |
| `users` | `{ "_id": "hashed" }` | равномерное распределение без hot spots |

### Компоненты

| Сервис | Тип | Роль |
|---|---|---|
| `pymongo-api` | FastAPI-приложение | единственная точка входа клиентов |
| `mongos` | MongoDB router | маршрутизирует запросы к нужному шарду |
| `configSrv` | MongoDB config server | хранит routing table кластера |
| `shard1` | MongoDB | хранит чётные hash-диапазоны orders и users |
| `shard2` | MongoDB | хранит нечётные hash-диапазоны orders и users |

### Команды инициализации

```js
sh.enableSharding("somedb")
sh.shardCollection("somedb.orders", { "user_id": "hashed" })
sh.shardCollection("somedb.users", { "_id": "hashed" })
```

## Вариант 2 — Репликация

**Файл схемы:** `task1_v2_replication.drawio`

Каждый шард превращается в replica set из трёх нод.

### Конфигурация replica set

| Параметр | Значение |
|---|---|
| Реплик на шард | 3 (1 primary + 2 secondary) |
| Протокол репликации | oplog (operation log) |
| Механизм выборов | Raft-based, кворум 2 из 3 |
| Устойчивость к отказам | 1 нода на шард |
| Read preference | `secondaryPreferred` — читаем с secondary, снижая нагрузку на primary |

### Сетевые взаимодействия

| Стрелка | Протокол / детали |
|---|---|
| `mongos → primary` | write (orders, users) |
| `mongos → secondary` | read (secondaryPreferred) |
| `primary → secondary` | oplog replication (push) |
| `secondary ↔ secondary` | heartbeat (2 сек), участие в выборах |

## Вариант 3 — Кэширование

**Файл схемы:** `task1_v3_cache.drawio`

Добавляется инстанс Redis между приложением и MongoDB.

### Стратегия кэша

| Параметр | Значение |
|---|---|
| Сервис | Redis (один инстанс) |
| Библиотека | `fastapi-cache` + `RedisBackend` (уже есть в `app.py`) |
| Кэшируемые данные | `products` — каталог товаров (список, отдельные позиции) |
| TTL | 60 секунд |
| Паттерн | Cache-aside: miss → читаем MongoDB, пишем в Redis |

### Почему products не шардируется, а кэшируется

Во время Чёрной пятницы тысячи пользователей одновременно читают **одни и те же** страницы каталога.
Шардирование это не решает — все запросы к одному товару всё равно идут на один шард.
Redis отвечает за микросекунды и полностью снимает нагрузку с MongoDB для read-heavy коллекций.

## Вариант 4 — API Gateway, Consul, горизонтальное масштабирование

**Файл схемы:** `task1_v4_scaling.drawio`

Один инстанс приложения — это SPOF. Решение: запустить несколько `pymongo-api`, поставить
перед ними балансировщик (API Gateway), и научить Gateway автоматически узнавать о новых/упавших
инстансах через Service Discovery.

### Новые компоненты

| Сервис | Тип | Роль |
|---|---|---|
| `API Gateway` | nginx / Traefik | принимает HTTPS-трафик от клиентов, балансирует на app-инстансы |
| `Consul` (3 ноды) | Hashicorp Consul | Service Discovery, реплицирует данные через Raft (кворум 2/3) |
| `pymongo-api-1`, `-2`, `-3` | FastAPI | stateless-инстансы приложения |

### Поток регистрации и обнаружения сервисов

```
1. pymongo-api-N стартует
        ↓
2. POST в Consul: "я pymongo-api на 10.0.0.X:8080, healthy"
        ↓
3. Consul реплицирует регистрацию через Raft на все 3 ноды
        ↓
4. API Gateway периодически (или через DNS) спрашивает Consul:
   "дай мне всех pymongo-api"
        ↓
5. Gateway получает актуальный список → перестраивает upstream pool
        ↓
6. Если инстанс падает / heartbeat пропадает → Consul помечает unhealthy
        → Gateway убирает его из балансировки
```

### Сетевые взаимодействия

| Стрелка | Протокол / детали |
|---|---|
| `Клиент → API Gateway` | HTTPS (443) или HTTP (8080) |
| `API Gateway → Consul` | Service discovery (HTTP API или DNS) |
| `API Gateway → pymongo-api-N` | Балансировка LB: round-robin / least-conn |
| `pymongo-api-N → Consul` | register + heartbeat (раз в 10 сек) |
| `consul ↔ consul` | Raft replication (метаданные сервисов) |
| `pymongo-api-N → redis` | cache GET/SET |
| `pymongo-api-N → mongos` | MongoDB queries (как раньше) |

### Что это даёт

| Проблема | Решение |
|---|---|
| Падение одного инстанса = простой | LB убирает unhealthy инстанс, остальные обслуживают трафик |
| Деплой без даунтайма | Поднимаем новый инстанс → регистрируется в Consul → Gateway добавляет его. Затем останавливаем старый |
| Не справляется с нагрузкой | Запускаем `docker compose up -d --scale pymongo_api=N` (или k8s scale) |
| Конфигурация LB вручную | Не нужна — Gateway узнаёт об инстансах автоматически |

### Почему именно 3 ноды Consul

Consul использует Raft для согласованности. Кворум `⌈N/2⌉ + 1`:
- 1 нода → нет fault tolerance
- 3 ноды → переживают падение 1 ноды (кворум 2/3)
- 5 нод → переживают падение 2 нод (кворум 3/5)

3 — стандартный production-минимум.
